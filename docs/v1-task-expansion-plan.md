# v1 Task Expansion Plan

Status: planning document for post-`v0.0` benchmark growth.

Start here: `docs/v1-readiness-checklist.md` defines the active-development
discipline, task acceptance criteria, stale-baseline policy, validation
commands, and rerun matrix that must be satisfied before v1 task/scoring
changes are treated as current comparable evidence.

The v1 target is 100+ total tasks across public and private splits while
preserving the benchmark's core evidence contract: replayable authorization
proof, boundary reasoning, and false-positive discipline on secure controls.

The current public-safe scale roadmap lives at
`artifact/v1-task-scale-roadmap.json`. It is planning evidence only: it maps the
54-task public split plus active and shadow protected-private pack waves to a
planned total above 100 tasks, but it does not satisfy the scale gate until real
manifests validate.

## Expansion Rules

- Treat v0.0 as frozen historical release evidence.
- Keep vulnerable tasks paired with meaningful secure controls.
- Preserve app coverage across project management, billing, support, file
  sharing, API tokens, and audit/settings.
- Do not compare old 46-task baselines against expanded task sets without a
  rerun.
- Treat public tasks as reproducibility tasks, not private leaderboard rows.
- Keep private holdout bodies, routes, seeds, and raw evidence out of public Git
  history.

## Candidate Workflow Families

| Family | Example vulnerable path | Required controls |
| --- | --- | --- |
| Billing plan change to entitlement misuse | A member changes plan or feature entitlement outside the permitted tenant boundary. | Owner success, cross-tenant denial, member denial where applicable. |
| Support ticket reassignment to unauthorized update | A lower-privilege actor reassigns or mutates another organization's ticket. | Same-org authorized update, cross-org denial, status-only safe path. |
| File share revoke to stale-link access | A revoked or downgraded share link still grants access. | Fresh-link allowed path, revoked-link denial, owner access control. |
| API token scope change to unauthorized export/read | A token with read-only or wrong-tenant scope exports sensitive data. | Correct-scope allow, wrong-scope denial, wrong-tenant denial. |
| Audit export cross-organization access | An export generated by one org is accessible from another org or role. | Export owner allow, non-admin denial, cross-org denial. |
| Invitation or role downgrade stale permissions | A downgraded member retains admin or write capability after role change. | Admin allow, downgraded-member denial, unrelated member denial. |

## 100-Task Scale Roadmap

The public split currently has 54 validated tasks. The remaining scale path
requires at least 46 additional validated tasks before any v1/community-scale
claim. The public-safe roadmap uses two protected-private waves:

| Wave | Split | Planned tasks | Purpose |
| --- | --- | ---: | --- |
| Active private holdout v1 pack | protected private active | 24 | Release-candidate scoring pack for repeated private no-tools and tool-agent evidence. |
| Shadow private holdout v1 pack | protected private shadow | 24 | Rotation, drift-check, and retirement candidate pack before future promotion. |

Those two planned waves would bring the total to 102 tasks once real manifests
exist and validate. Until then, the roadmap is only a planning artifact; it must
not be counted as private holdout evidence, repeated private evidence, or a
passed `v1_task_scale` gate.

## Quality Gates For New Tasks

- Each vulnerable task names expected boundary keys.
- Each task has scorer-owned replay checks.
- Secure controls use `findings: []` as the expected agent behavior.
- Controls cover both denial and authorized-allow behavior where applicable.
- Route aliases and decoys are present without making the task ambiguous.
- The task is documented in the quality matrix and release evidence before any
  release-style claim.

## Baseline Policy

Once task count or scoring semantics change:

- mark old 46-task baselines stale for current comparisons;
- keep old v0.0 baselines visible as historical evidence only;
- rerun the scripted harness sanity check;
- rerun repeated public model/tool-agent families before comparing scores;
- regenerate public-safe charts and paper tables;
- update `docs/status.md`, `docs/benchmark-spec.md`, and
  `docs/claims-and-evidence.md`.
