# Multi-Step Workflow Task Plan

AuthZBench-SaaS should grow toward tasks that look like real SaaS authorization
workflows, not only isolated endpoint checks.

## Why This Matters

Single-request tasks are useful for early scoring, but serious agents should be
tested on stateful workflows where the authorization boundary appears after a
sequence of normal SaaS actions.

Multi-step tasks should still be deterministic and scorer-owned: the agent can
investigate, but the final pass/fail result must come from replayable backend
evidence.

## Candidate Workflow Families

- invite created, accepted, downgraded, then used across tenant boundaries
- role changed from admin to member, followed by stale privileged action
- API token created with limited scope, then reused on admin or export routes
- share link revoked, then accessed through an alias or cached route
- audit export generated by one org, then fetched by another actor
- billing plan changed by member, then verified through account settings
- support ticket reassigned, then updated by an actor outside the owning org
- file permission changed, then downloaded through a workspace alias

## App Coverage Targets

- project management: role downgrade, task reassignment, project export
- support desk: ticket ownership, invite lifecycle, status update authority
- billing admin: plan changes, invoice exports, entitlement boundaries
- file sharing: revoked links, workspace files, document aliases
- audit logs: org settings, audit exports, compliance previews
- API token vault: token scopes, secret reads, export access

## Task Design Requirements

Every multi-step task should include:

- one clear authorization boundary
- a normal setup sequence with no hidden external dependency
- one vulnerable path or one secure-control path
- scorer-owned replay proof
- `evidence_requirements` for vulnerable tasks that must prove each required
  replay step before exploit-proof credit is awarded
- expected request shape plus response expectations for every required evidence
  step, so a repeated final exploit request cannot masquerade as setup proof
- at least one decoy action that is plausible but not sufficient
- a secure-control counterpart when practical
- no need for brute force, credential theft, social engineering, or external
  network access

## First Implementation Wave

The first landed public wave starts with project management:

- one vulnerable task that requires a normal same-tenant task update followed by
  a cross-tenant workspace-alias read
- one authorized-allow control for the matching owner update workflow

This first wave enforces multi-step evidence sequencing. The setup action is an
authorized workflow context step, not yet a causal prerequisite that unlocks the
exploit path. Causal stateful chains are a follow-on v0 hardening target.

For the broader task-growth cycle, prioritize 12 public tasks:

- 6 vulnerable multi-step tasks, one per app family
- 6 secure controls, one per app family
- at least 3 authorized-allow controls
- at least 3 denial controls

This wave should land in app-sized commits so reviewers can inspect each
workflow independently.

## Review Bar

Before a workflow family is marked release-ready:

- validate manifests
- run scorer replay
- run one scripted baseline
- run one no-findings control baseline
- apply `docs/task-quality-rubric.md`
- record a short public review note under `docs/reviews/`

The goal is not more tasks for their own sake. The goal is better evidence that
an agent understands SaaS authorization state, actor context, and backend proof.
