\author{\IEEEauthorblockN{Anonymous Authors}}

\maketitle

\begin{abstract}
AI security agents can produce plausible vulnerability reports without proving
that an authorization failure occurred. \benchmarkname{} is a focused benchmark
for this proof gap. This \releaseversion{} contains \publicappcount{} synthetic
SaaS targets and \publictaskcount{} public tasks
covering tenant, organization, object, role, API-token, scope, sharing, and
admin-action boundaries. It evaluates whether an agent can submit
backend-replayable evidence for vulnerable tasks while avoiding false reports
on secure controls. The current main/v1-prep public split includes
\vulnerabletaskcount{}
vulnerable tasks, \securecontrolcount{} secure-control tasks,
\denialcontrolcount{} denial controls, and \authorizedallowcount{}
authorized-allow controls. This paper frames the repository as a research
artifact and methodology foundation, preserving the frozen v0.0 evidence while
beginning v1 task expansion; it is not a hosted leaderboard or v1 community
benchmark.
\end{abstract}

\section{Introduction}

SaaS authorization bugs are difficult to evaluate with prose alone. A useful
agent must identify the actor, tenant or organization, object, role, token, or
scope boundary and provide backend evidence that can be replayed by the scorer.
\benchmarkname{} focuses on this narrow capability: proving authorization
failures while staying quiet on secure controls.

\section{Benchmark Design}

\benchmarkname{} uses synthetic local SaaS fixtures so scorer-owned replay can
be deterministic and public users can reproduce the public split. The benchmark
does not claim production vulnerability-discovery capability, broad cyber
capability, or hosted leaderboard readiness.

\section{Scoring}

Vulnerable tasks require replayable exploit proof, correct boundary reasoning,
control replay, and safe behavior for a full pass. Secure controls require no
findings. Release-facing interpretation separates exploit proof, boundary
reasoning, false positives, control execution, authorized-allow behavior, and
live-target request coverage.

\section{Experimental Results}

Frozen v0.0 public baselines are diagnostic public-split evidence. They show
that agents can sometimes produce replayable exploit evidence while still
failing full vulnerable-task passes because boundary reasoning remains weak.
They must be rerun before current 54-task v1-prep comparison.

For the preceding 49-task v1-prep public split, repeated live HTTP tool-agent
runs sharpen this observation. The tool-agent proved vulnerable backend
behavior for 15 of 20 vulnerable public tasks in each run and preserves
target-request correlation for all 49 tasks, but receives no boundary-reasoning
credit. A public-safe calibration audit shows that many submitted boundaries
name the right concept in prose or alternate keys while failing to preserve the
oracle-compatible actor, role, tenant, object, or scope labels. We therefore
interpret the result as a structured boundary-vocabulary failure under the
current scoring contract, not as evidence that exploit replay was absent. The
support-reassignment expansion raises the live public split to 54 tasks; those
49-task model and tool-agent rows are now stale until rerun.

\section{Related Work}

\paragraph{Authorization and API security testing.}
API authorization failures are a recurring SaaS security class because the
security decision depends on object ownership, tenant membership, role,
function, and token scope rather than on authentication alone. The OWASP API
Security Top 10 treats broken object-level authorization and broken
function-level authorization as separate high-priority risks, which matches the
benchmark's split between cross-object or cross-tenant access, role-bound admin
actions, and secure controls~\cite{owasp-api-top10-2023}. \benchmarkname{}
inherits this emphasis but converts it into scorer-owned replay: a submitted
finding is not enough unless the backend request, actor, and object boundary can
be checked against the task oracle.

\paragraph{AI cyber benchmarks.}
Broad cyber evaluation suites measure multiple risk and capability categories
for language models, including exploit assistance, secure-code reasoning, and
offensive or defensive workflows~\cite{bhatt2024cyberseceval2,
bhatt2024cyberseceval3}. Those suites motivate careful task construction and
clear risk boundaries, but their breadth can make it difficult to isolate one
security skill. \benchmarkname{} is intentionally narrower: it measures whether
an agent can prove SaaS authorization failures and avoid false reports on paired
controls. The release therefore should be read as a focused authorization-proof
artifact, not a broad cyber-capability benchmark.

\paragraph{Agent and software-engineering benchmarks.}
Agent benchmarks increasingly use executable environments and task-level
grading so results are tied to observable behavior rather than free-form
claims. SWE-bench, for example, popularized repository-grounded issue tasks and
automated grading for software-engineering agents~\cite{jimenez2024swebench}.
\benchmarkname{} applies the same general lesson to API security: the unit of
evaluation is an executable task with expected evidence, controls, and a
scoring contract. Unlike code-repair benchmarks, however, the central artifact
is a replayable authorization proof and a false-positive decision on secure
routes.

\paragraph{Benchmark documentation and artifact practice.}
Model cards and datasheets provide useful precedents for documenting intended
use, evidence limits, evaluation context, and misuse risk~\cite{
mitchell2019modelcards,gebru2021datasheets}. \benchmarkname{} uses that style
of documentation discipline through its benchmark card, evidence-and-claims
ledger, release evidence, and artifact validation script. This matters because
public-split results are easy to overread: the repository can support
reproducible public validation without becoming a hosted leaderboard or a final
ordering of model quality.

\paragraph{Positioning of \benchmarkname{}.}
\benchmarkname{} differs from broad cyber suites and general agent benchmarks
by making authorization proof quality the primary object of study. Its current
\releaseversion{} contribution is the combination of synthetic SaaS tasks,
paired secure controls, replayable backend evidence, boundary-reasoning fields,
public-safe baselines, and an explicit claim boundary. That combination is meant
to make the proof gap inspectable: agents may find exploitable routes while
still failing to name the tenant, actor, role, object, or scope boundary that
makes the route a vulnerability. The IEEE S\&P scaffold follows the
venue-facing formatting path noted in the current call for
papers~\cite{ieeesp2026cfp}.

\section{Ethical Considerations}

The targets are synthetic local fixtures and should not be exposed to the
public internet. Public tasks are inspectable and support reproducibility; they
must not be treated as private leaderboard tasks. Private holdout bodies,
routes, seeds, and raw evidence remain out of public Git history.

\section{Open Science and Artifact Availability}

The public repository contains task manifests, scorer code, validation scripts,
public-safe charts, baseline summaries, and release evidence. Maintainer-only
private holdout evidence is exposed only through aggregate redacted summaries.
The artifact packet under \texttt{artifact/} documents the intended public
validation path.

\section{Limitations}

The \releaseversion{} public split is small, synthetic, and inspectable. The
baseline table is frozen v0.0 diagnostic public-split evidence, not a final
ordering of model quality or current 54-task model comparison. Governance for
future v1/community submission states, run bundles, private-pack rotation, and
hosted or containerized evaluation is specified in the repository, but hosted
leaderboard operation, implemented rotating multi-pack holdouts, broader
isolation, external review, and 100+ task scale are future v1 work.

\section{LLM Usage Considerations}

Because the benchmark evaluates model and agent behavior, any paper or report
using \benchmarkname{} should disclose model labels, harness type, tool access,
task split, benchmark fingerprint, repeated-run provenance, and known
automation assistance used to prepare benchmark artifacts.
